One billion parameters weigh 2 GB in bf16, 1 GB in FP8, half a GB in MXFP4. The roster lives in all three: bf16 baselines from 2023, FP8 flagships in GLM-5.3 and V4.1-Flash, MXFP4 experts in gpt-oss-120B and Kimi-K3. This chapter weighs the same billion params three ways on channel A against B, then reads what each config actually records: format, block size, and what stays unconverted.

22.1Same params, three weights

Formats are bytes per number with rules about range and precision. bf16 spends 16 bits everywhere; FP8 spends 8 with a narrower range that needs per-block scales; MXFP4 spends 4 with microscaling the kernels must understand. The figure's bars are exact: bytes equal params times width. Quality at each width is a separate, measured question the course doesn't answer from arithmetic.

22.3Blocks, not tensors

Narrow formats scale per block, not per tensor: 128 consecutive weights share one FP8 scale in GLM-5.3, 32 in V4.1-Flash. Smaller blocks track outliers better and cost more scale metadata; the 4x difference is a precision-against-overhead dial the two vendors set differently. gpt-oss's exception list is the other half of the design: attention, routing, embeddings and the LM head stay precise while experts go narrow, because errors in routing compound across every token while errors in one expert touch few. Read any quantization_config as two decisions — how narrow, and what escapes.

22.4The cache can go narrow too

Weights are half the memory story; chapter 20's receipts are the other half, and they halve the same way. Qwen2.5-7B's 57,344 B per token in bf16 is 28,672 B in FP8 — pure arithmetic, same bytes-per-number rule. Whether an engine offers the narrower cache, and which kernels read it on which GPU, is serving configuration: chapter 29's table, not this chapter's claim. The principle travels: every byte count in this course carries an implicit "at stated precision," and narrowing is the cheapest multiplier available.

Easy to get wrong

Quantization method is not model quality. A 4-bit expert can out-reason a bf16 dense block three times its active size, and often does on the 2026 scoreboard. Bits price memory and bandwidth; benchmarks price answers. Never convert one into the other without a measurement.

22.6Check yourself

One billion weights occupy how much in bf16, FP8 and MXFP4?

  1. 1 GB, 1 GB, 1 GB — formats don't change size
  2. 2 GB, 1 GB, 0.5 GB — params times byte width
  3. 4 GB, 2 GB, 1 GB — formats double-count
  4. 0.5 GB in all three — packing is universal
2, 1 and 0.5 bytes per number respectively. gpt-oss-120B's 65.25 GB on disk for 120B params sits just above the 60 GB floor — MXFP4 plus scales and exceptions.

Why does gpt-oss leave attention, the router, embeddings and the head unconverted?

  1. Those parts have no weights
  2. MXFP4 kernels can't run them at all
  3. Errors there compound across every token, while one expert's error touches few
  4. The config format requires four exceptions
Precision follows blast radius. Routing and attention shape every token downstream; a single expert shapes its visitors. The exception list is the design.

GLM-5.3 scales FP8 per 128 weights, V4.1-Flash per 32. What does the smaller block buy?

  1. Finer tracking of outliers at the cost of more scale metadata
  2. Four times fewer weights
  3. A larger context window
  4. Compatibility with bf16 kernels
Block size is a precision-against-overhead dial. Outliers get their own scale sooner in 32-wide blocks; the metadata bill grows 4x.

Qwen2.5-7B's 57,344 B/token KV receipt in FP8 would be?

  1. 57,344 B — caches can't narrow
  2. 114,688 B — narrowing doubles traffic
  3. 7,168 B — one eighth
  4. 28,672 B — half the bytes, same arithmetic as weights
Bytes halve with precision everywhere, cache included. Whether an engine offers it is serving configuration — chapter 29.
Takeaways
  • 2, 1, 0.5 bytes per param: bf16 baselines, FP8 flagships, MXFP4 experts. Disk bytes corroborate.
