Grouped-query attention shares heads. Multi-head latent attention stops storing heads at all — and Kimi-K3 and GLM-5.3 still store exactly this trick at trillion scale. It debuted in DeepSeek-V2-Lite: one 512-number latent plus a 64-number rotary key per token, with every head reconstructing what it needs at read time. Kimi-K2 scaled the same ranks to 61 layers and 384 experts. This chapter caches one token twice: Qwen2.5-7B's grouped KV on channel A, V2-Lite's latent on channel B.

The 2-minute version

MLA compresses each token's keys and values into one 512-number latent plus a 64-number rotary key, stored instead of per-head KV. Reads expand the latent per head — compute against a small cache beats streaming a big one. Same ranks from V2-Lite to Kimi-K3.

After this chapter you can: compute latent bytes from rank keys · explain why the rotary key stays decoupled · describe the expand-at-read decode saving.

8.1One latent instead of a thousand numbers

Count what gets stored per layer. Qwen2.5-7B writes 4 heads × 128 keys plus 4 × 128 values: 1,024 numbers. V2-Lite writes a 512-number latent plus a 64-number rotary key: 576 numbers, 44% fewer, and the gap widens against wider GQA. Across 27 layers that is 31,104 B per token in bf16 against Qwen's 57,344 B — with 16 query heads served, not 4.

8.2Compress, split, rotate separately

The compressor is one projection shared across heads, then a split along the rank. The rotary half never enters the latent; it rotates on its own path:

The split sizes are config values: 128 content dims and 64 rotary dims , with values at width 128 . Decoupling matters because rotation and compression want different things: the rotary key must stay comparable across positions, while the latent only has to reconstruct per-head content at read time. V3 adds a low-rank query projection on the same pattern (rank 1,536 ) so large query heads compress too.

8.3Expand at read time

Storing less only helps if reading costs less too. V3's attention projects the cached latent back up per head inside the forward pass — the same compress-once, expand-at-read shape as V2, with the query side compressed as well:

Follow the tensors: kv_a_proj_with_mqa compresses hidden to rank 512 plus rotary once per token; at read time kv_b_proj expands the normalized latent to every head's content and value width. The expand runs per query against a small cached latent instead of streaming full per-head KV — that is the decode saving, in code rather than in prose. Prefill can instead reconstruct full keys and values and run standard attention; the two modes are mathematically the same attention with different memory traffic, which is why engines pick per phase.

Easy to get wrong

MLA is not fewer heads. V3 configures 128 query heads and 128 KV heads and caches neither as such; the latent replaces both. Dividing hidden by heads to get a head dim, the chapter-6 habit, gives 56 here and means nothing — read the rank keys.

8.4Kimi-K2 scales the ranks

Kimi-K2 keeps V3's ranks (512 latent, 1,536 query ) and its 61 layers , narrows to 64 query heads , and triples the routed experts to 384 . Latent bytes per token match V3 exactly at 70,272. The next step drops position embeddings from the MLA layers entirely and pairs them with linear attention — Kimi-K3, chapters 10 and 18.

8.7Check yourself

How many numbers does DeepSeek-V2-Lite cache per layer per token?

  1. 1,024: 16 heads × 128 × 2
  2. 576: a 512-number latent plus a 64-number rotary key
  3. 128: one head's worth
  4. 64: the rotary key alone
512 + 64 = 576, against 1,024 for a 4-head GQA layer. The 16 KV heads in the config never materialize as cached tensors.

Why does the rotary key stay out of the latent?

  1. Rotary keys are too large to compress
  2. The latent can only hold 512 numbers
  3. Rotation must stay comparable across positions, while content only reconstructs per head
  4. RoPE is disabled in MLA models
Position comparison and content reconstruction are different jobs. The code rotates q_pe/k_pe on a separate path and expands it across the content batch.

What does kv_b_proj do at read time?

  1. Expands the normalized latent to every head's key and value width
  2. Compresses the queries into the latent
  3. Selects which tokens to attend to
  4. Applies rotary embeddings to the latent
One cached latent in, per-head keys and values out — computed per query instead of streamed from memory. That trade is the whole decode saving.

Kimi-K2 and DeepSeek-V3 cache how many latent bytes per token in bf16?

  1. 31,104 — the V2-Lite number
  2. 57,344 — the Qwen2.5 number
  3. 131,072 — the Mistral number
  4. 70,272 — the same 576 numbers over 61 layers
(512 + 64) × 2 B × 61 layers = 70,272 B. Same ranks as each other, more layers than V2-Lite's 27.

From chapter 6: gpt-oss-120B repeats each KV head 8 times. Why is its cache still small?

  1. It caches a latent like MLA models
  2. Narrow heads (64) times a 128-token window cap the multiplication
  3. It has only 8 layers
  4. Its KV heads are shared across requests
73,728 B per token that never multiplies past 128 positions. Two halvings — head width, then window — on top of grouped heads.
Takeaways
  • MLA caches a low-rank latent plus a decoupled rotary key: 576 numbers where GQA keeps 1,024.
  • Compress once per token, expand per head per query — running the expand instead of streaming KV is the decode saving.
  • Head counts in MLA configs describe queries, not the cache; read the rank keys.
  • Sparse selection on top of MLA is chapter 9; dropping positions is chapter 10.
