About the course

How this course is checked

Every config key, class, line number and model dimension points at one pinned release of Transformers and one pinned revision of each roster config. Here is how that is kept true.

1What is pinned

The course is written against exact revisions, not against "the latest version". Channel A in every figure is the incumbent design and channel B is the challenger. Every pin lives in one file, course.json, with the date the course was last checked: {{checked}}.

scripts/fetch-sources.mjs makes a shallow clone of every code repository at exactly its pinned commit, and downloads the listed model files at exactly their revision, into .cache/src/.

Scope, stated once: model in this course means decoder-era language models from November 2022 on — the architectures that serve chat, code, agents and reasoning today. Encoder-only and encoder-decoder classics (BERT, T5), convolutional vision backbones and GAN image generators are out of scope, not oversights: they predate the course's window or belong to other tracks. Within the window, the course pins what it can fetch and cites the rest as deltas; the attention zoo maps every variant to one of those three statuses.

2References are verified by the build

Chapters never paste source code by hand. They use two build-time tags:

  • A reference names a file, a line and a symbol, in the pinned code or a model's files. The build opens the file at the pinned commit or revision, checks that the line exists, and checks that the symbol appears on it or within two lines. The rendered link is a permalink to that commit, on GitHub or on Hugging Face, so it keeps pointing at the right line after the projects move on.
  • An excerpt names a file and line ranges. The build copies those lines verbatim from the pinned file, highlights them, and numbers them with their real line numbers.

A strict build fails if any reference or excerpt doesn't resolve. The resolved excerpts are also written to a lockfile, so the published site can be rebuilt without downloading the sources, while the check that runs on every change still verifies everything against the clones, along with every internal link and anchor.

node scripts/fetch-sources.mjs # pinned clones and model files node scripts/build.mjs --strict # every ref, symbol and excerpt node scripts/check-links.mjs # every internal link and #anchor LAB_SOLUTION=1 uv run pytest labs # every lab's reference solution node scripts/check-labs-pyodide.mjs # the same labs in Pyodide, as the browser runs them

3Research maps come first

Before a chapter is written, the facts it needs are collected in source maps under research/. architectures.md is the year-by-year timeline with links to every paper, release note and explainer. models.json derives every roster model's dimensions, KV and state bytes from the pinned configs, with the method beside each number. curriculum.md fixes which two designs each chapter runs. The citations in the maps were checked by hand against the web in October 2026, and a chapter still re-opens the file before it quotes it.

4What kind of number each one is

Every number is one of these, and the text says which.

  • Read from config or code. A head count, an expert count, a rank, bytes per token: stated as a fact, with a reference to the pinned line next to it. Capacity worked out from these is arithmetic, and every assumption in the budget is named.
  • A vendor specification. The vendor's own figure, always with the SKU.
  • A floor. A bound no real run can beat, from specifications and exact byte and FLOP counts. A step can be no faster than the longer of reading its bytes at full bandwidth and doing its arithmetic at peak FLOPS; the two overlap, so they are not added. Figures drawn on this clock say "floor" on the axis and in the caption.
  • Measured. Only from bench/, with the machine, the versions and the command next to the result, or from a linked publication, attributed, with its hardware and caveats.
  • A parameter you set. Where a figure depends on something the course cannot know, you choose the value, and the result reads as "if this, then that".

5Figures are simulations

The step-through figures are not drawings. Each one runs a small JavaScript model of the rule it shows: head counts, expert picks, cache bytes, denoising masks. Every step is derived from that model, and each rule in the code carries a comment naming the source line it mirrors.

A step is marked Δ only when the two designs compute something different at that point. Steps marked = are ones where they agree.

6Labs test shapes and invariants

The labs build on a two-layer transformer in pure Python plus fixture configs copied from the pinned revisions. Most labs check shapes and counts against the real configs, and the refactor labs check the property every equivalent rewrite must keep: the logits don't change. Every lab also runs locally:

uv run pytest labs/ch01_block_shapes # your code LAB_SOLUTION=1 uv run pytest labs # every reference solution

7Drift, re-pinning and editions

A new edition ships every eight weeks. New architectures arrive as cited deltas first and join the pinned roster when their configs are publicly fetchable, and the source review is repeated chapter by chapter. Between editions, a drift check carries references across to new commits and lists every reference that needs a read. Model revisions that need authentication are moved by hand.

node scripts/repin.mjs hf-transformers v5.10.0 --write # carry refs across through git's diff node scripts/fetch-sources.mjs # clone the new commits into .cache/src node scripts/build.mjs --strict # lists every reference that still needs a read
